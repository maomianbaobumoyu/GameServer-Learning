## TCP 的 11 种状态（按生命周期分阶段）

TCP 的状态可以分为「连接建立、数据传输、连接释放」三个阶段，我按流程拆解每个状态的含义：

![image-20260529153029788](C:\Users\不二家sir\AppData\Roaming\Typora\typora-user-images\image-20260529153029788.png)

### 1. 连接建立阶段（三次握手）

![image-20260529160047524](C:\Users\不二家sir\AppData\Roaming\Typora\typora-user-images\image-20260529160047524.png)

这一阶段的目标是让客户端和服务器同步序列号，建立可靠连接。

|     状态      |                             含义                             |                           典型场景                           |
| :-----------: | :----------------------------------------------------------: | :----------------------------------------------------------: |
|   `LISTEN`    |            服务器在监听端口，等待客户端的连接请求            |               服务器调用`listen()`后进入此状态               |
|  `SYN_SENT`   |    客户端已发送`SYN`包（第一次握手），正在等待服务器回复     |              客户端调用`connect()`后进入此状态               |
|  `SYN_RCVD`   | 服务器收到客户端的`SYN`，并回复了`SYN+ACK`（第二次握手），正在等待客户端的`ACK` |                 服务器收到`SYN`后进入此状态                  |
| `ESTABLISHED` |         三次握手完成，连接建立成功，可以开始传输数据         | 客户端收到`SYN+ACK`并回复`ACK`、服务器收到`ACK`后，双方都进入此状态 |

*补充：图中还有 “同时打开” 的情况 —— 客户端和服务器同时向对方发送`SYN`，双方都会进入`SYN_RCVD`，再通过互相回复`SYN+ACK`进入`ESTABLISHED`，这种场景非常少见。*

------

### 2. 数据传输阶段

只有一个核心状态：`ESTABLISHED`

- 此时连接是活跃的，双方可以互相发送、接收数据，是 TCP 连接的 “工作状态”。

------

### 3. 连接释放阶段（四次挥手）

![image-20260529155415948](C:\Users\不二家sir\AppData\Roaming\Typora\typora-user-images\image-20260529155415948.png)

（服务器发送的`FIN`包，**本身就必须携带 ACK 标志位**，所以报文6带有ack）

TCP 是全双工协议，关闭连接需要双方都确认断开，因此是 “四次挥手”。这里要区分「主动关闭方」和「被动关闭方」的流程：

#### （1）被动关闭方（典型是服务器，图中右侧虚线框）

当客户端主动发起关闭时，服务器的流程：

1.  ESTABLISHED → 收到客户端的 FIN 包（第一次挥手），回复ACK

   （第二次挥手） → 进入 CLOSE_WAIT状态。

   - `CLOSE_WAIT`：服务器知道客户端要关闭了，但自己可能还有数据没发完，需要等应用层调用`close()`。

2. 应用层调用`close()`，发送`FIN`包（第三次挥手） → 进入`LAST_ACK`状态。

3. 收到客户端的`ACK`（第四次挥手） → 进入`CLOSED`状态，连接彻底关闭。

#### （2）主动关闭方（典型是客户端，图中左侧虚线框）

客户端主动发起关闭的流程：

1. `ESTABLISHED` → 应用层调用`close()`，发送`FIN`包（第一次挥手） → 进入`FIN_WAIT_1`状态。
2. 收到服务器的`ACK`（第二次挥手） → 进入`FIN_WAIT_2`状态，等待服务器的`FIN`包。
3. 收到服务器的 FIN 包（第三次挥手），回复  ACK （第四次挥手） → 进入 TIME_WAIT 状态。
   - `TIME_WAIT`：会等待 **2MSL（最长报文寿命的 2 倍）**，目的是确保服务器收到了自己的`ACK`，防止旧数据包干扰新连接。
4. 2MSL 时间结束 → 进入`CLOSED`状态。

*补充：图中还有 “同时关闭” 的情况 —— 双方同时调用`close()`，都发送`FIN`包，然后互相回复`ACK`，进入`CLOSING`状态，再通过收到对方的`ACK`进入`TIME_WAIT`，最终关闭连接。*

## 客户端 + 服务器的完整流程

结合图里的粗线，串一遍典型的 HTTP 请求流程：

1. 服务器：`CLOSED` → `socket()`→`bind()`→`listen()` → `LISTEN`状态（监听 80 端口）。
2. 客户端：`CLOSED` → `socket()`→`connect()` → 发`SYN` → `SYN_SENT`状态。
3. 服务器收到`SYN`，回复`SYN+ACK` → `SYN_RCVD`状态。
4. 客户端收到`SYN+ACK`，回复`ACK` → `ESTABLISHED`状态，开始发 HTTP 请求。
5. 服务器收到`ACK` → `ESTABLISHED`状态，处理请求并返回响应。
6. 客户端收到响应，调用`close()`，发`FIN` → `FIN_WAIT_1`状态。
7. 服务器收到`FIN`，回复`ACK` → `CLOSE_WAIT`状态，继续处理完剩余数据。
8. 客户端收到`ACK` → `FIN_WAIT_2`状态，等服务器的`FIN`。
9. 服务器处理完数据，调用`close()`，发`FIN` → `LAST_ACK`状态。
10. 客户端收到`FIN`，回复`ACK` → `TIME_WAIT`状态，等待 2MSL。
11. 服务器收到`ACK` → `CLOSED`状态，关闭连接。
12. 客户端 2MSL 时间到 → `CLOSED`状态，连接彻底关闭。

------------------------

1. **`CLOSE_WAIT` 过多**：说明被动关闭方（比如服务器）收到了对方的`FIN`，但应用层一直没调用`close()`，可能是程序逻辑有 bug，导致连接无法正常关闭，占用资源。
2. **`TIME_WAIT` 过多**：主动关闭方（比如客户端）关闭后会进入此状态，等待 2MSL。如果服务器作为主动关闭方，大量`TIME_WAIT`会占用端口资源，影响服务性能（可以通过调整内核参数优化）。



## TIME_WAIT状态

客户端连接在收到服务器的结束报文段（TCP 报文段 6）之后，并没有直接进入 CLOSED 状态，而是转移到 TIME_WAIT 状态。在这个状态，客户端连接要等待一段长为 2MSL（Maximum Segment Life，报文段最大生存时间）的时间，才能完全关闭。

TIME_WAIT 状态存在的原因有两点：

- 可靠地终止 TCP 连接。
- 保证让迟来的 TCP 报文段有足够的时间被识别并丢弃。

第一个原因很好理解。假设用于确认服务器结束报文段 6 的 TCP 报文段 7 丢失，那么服务器将重发结束报文段。因此客户端需要停留在某个状态以处理重复收到的结束报文段（即向服务器发送确认报文段）。否则，客户端将以复位报文段来回应服务器，服务器则认为这是一个错误，因为它期望的是一个像 TCP 报文段 7 那样的确认报文段。

在 Linux 系统上，一个 TCP 端口不能被同时打开多次（两次及以上）。当一个 TCP 连接处于 TIME_WAIT 状态时，我们将无法立即使用该连接占用着的端口来建立一个新连接。反过来思考，如果不存在 TIME_WAIT 状态，则应用程序能够立即建立一个和刚关闭的连接相似的连接（这里说的相似，是指它们具有相同的 IP 地址和端口号）。这个新的、和原来相似的连接被称为原来的连接的化身（incarnation）。新的化身可能接收到属于原来的连接的、携带应用程序数据的 TCP 报文段（迟到的报文段），这显然是不应该发生的。这就是 TIME_WAIT 状态存在的第二个原因。

有时候我们希望避免 TIME_WAIT 状态，因为当程序退出后，我们希望能够立即重启它。但由于处在 TIME_WAIT 状态的连接还占用着端口，程序将无法启动（直到 2MSL 超时时间结束）。

客户端一般使用系统自动分配的临时端口号来建立连接，而由于随机性，临时端口号一般和程序上一次使用的端口号（还处于 TIME_WAIT 状态的那个连接使用的端口号）不同，所以客户端程序一般可以立即重启。

如果是服务器主动关闭连接后异常终止，则因为它总是使用同一个知名服务端口号，所以连接的 TIME_WAIT 状态将导致它不能立即重启。可以通过 socket 选项 SO_REUSEADDR 来强制进程立即使用处于 TIME_WAIT 状态的连接占用的端口。

> 四次挥手中，**主动发起 FIN 包、最后回复 ACK 确认对方 FIN 的那一方**，才会进入 TIME_WAIT 状态，等待 2MSL 时间。

也就是说：

- 谁先调用 `close()` 发送 FIN，谁就是主动关闭方；
- 主动关闭方在收到对方的 FIN 并回复 ACK 后，必须进入 TIME_WAIT；
- 被动关闭方（收到 FIN 后才调用 `close()` 发送 FIN 的一方），收到对方的 ACK 后会直接进入 CLOSED，**不会进入 TIME_WAIT**。
